# 开源范围与脱敏流程（OSS Scope and Sanitization）

> 适用对象：`compute-tycoon` 公开镜像仓库。本文说明生产仓库 → 公开镜像的取舍与脱敏规则，是开源治理的入口文档。

## 1. 流程总览

生产仓库（内部）与公开镜像（本仓库）是两个独立 Git 仓库：

1. **内部生产仓库**：包含完整开发历史、私密发布候选、商店物料、评审证据与内部路径信息，只在本机/内部网络维护。
2. **快照基线**：按公开范围选定一个已通过的发布候选，生成一次性的基线快照提交，作为公开镜像的单一根提交。
3. **公开镜像仓库（本仓库）**：只包含公开范围内容，从基线快照继续演进；此后所有公开提交都以脱敏为前提。

```text
内部生产仓库（完整历史）
  └─ 选定公开基线（版本/内容经治理裁决）
       └─ 一次性基线快照（无生产历史）
            └─ 公开镜像仓库（仅公开范围，持续维护）
```

## 2. 公开范围（包含项）

### 2.1 源码

- `src/`：游戏全部 TypeScript 源码（应用、核心引擎、经济、数据、平台适配、渲染、存档、评审检查点等）。
- `tests/`：单元测试（`tests/unit/`）与端到端测试（`tests/e2e/`）。
- `scripts/`：构建、评审、浏览器验证、经济模拟等脚本；脚本运行产生的临时日志文件不属公开必要内容，按维护节奏清理。
- 构建与工程配置：`package.json`、`package-lock.json`、`tsconfig.json`、`vite*.config.ts`、`vitest*.config.ts`、`index.html` 等。

### 2.2 文档子集

- 产品合同：`docs/PRODUCT_CONTRACT.md`（历史工程合同）与 `docs/product/H5_FINAL_PRODUCT_CONTRACT.md`（Release Candidate 权威产品合同）。
- 工程契约：`docs/SAVE_CONTRACT.md`、`docs/ECONOMY_SIMULATION.md`。
- 治理文档：`docs/oss/`、`docs/ai-development/` 全部内容。
- 经逐个审阅、确认不含私密信息的报告与产品文档（如技术报告、验收清单、资产来源报告）。
- 本仓库已存在的 `docs/oss/THIRD_PARTY_AND_ASSET_LICENSE_AUDIT.md` 作为第三方与资产许可审计记录保留；`docs/oss/SECURITY_AND_SECRET_AUDIT.md` 作为发布前脱敏审计工作清单保留（其内容含待排除项的具体标识，发布前按清单执行脱敏）。

### 2.3 `public/` 中的可公开资产

- 程序化/自有代码产物：lucide 许可文本（`public/third-party/lucide-LICENSE.txt`）、程序化合成音效。
- AI 原创生成且记录在案的媒体：Stage 1–5 五首独立 BGM、戴森终局主视觉。
- 媒体授权边界见 `docs/oss/THIRD_PARTY_AND_ASSET_LICENSE_AUDIT.md`；正式开源前需权利方/法务复核媒体与平台条款。

## 3. 排除清单（不进入公开镜像）

### 3.1 `store-materials/`（整体排除）

- 包含平台商店品牌物料、截图、评审证据、视频帧与平台应用相关材料，不属于开源范围，整体排除。
- 公开镜像中不得以任何形式收录或引用其内容；正式发行版物料另行许可。

### 3.2 含私密信息的原始文档

以下类别文档在进入公开镜像前必须逐个审查，含私密信息的一律排除或改写后放行：

- 含本机绝对路径（任何 `/<user>/...` 或 `<盘符>:\...` 形式）的报告与交接文档。
- 含私密评审站点/内网地址（形如 `https://<private-host>/`）的文档。
- 含平台应用 ID、开发者 ID、广告位 ID、账号标识等运营标识的文档（引用时一律使用占位符，如 `<app-id>`、`<ad-space-id>`）。
- 含真实姓名、邮箱、账号等个人信息的文档。
- 含未公开产品决策或超出首版范围讨论的设计文档（如终局/无尽设计预备、平台能力审计中的内部结论）。

### 3.3 评审与发布证据（evidence 策略）

- `evidence/` 下的浏览器矩阵、soak、自然流程、迁移等 JSON 结果：**默认不公开**。
- 原因：结果内含运行环境信息（本地地址、时间戳、模拟数据）与内部评审口径；公开价值低、泄漏面大。
- 公开镜像保留"如何复现"而非"当时的结果"：通过 `docs/` 中的验证方法与 `scripts/` 中的脚本说明即可由任何人复现。
- 若未来需要公开某项证据，须先做字段级脱敏（移除地址、时间戳、存档值）并经治理确认。

### 3.4 其他

- `node_modules/`、`dist*/` 等构建产物（已在 `.gitignore`）。
- 个人工程文件（`findings.md`、`progress.md`、`task_plan.md` 等 planning 产物不属于公开内容）。
- `.openai/` 等宿主/平台配置（按公开仓库需求另行评估，默认不公开）。

## 4. 脱敏规则（Sanitization Rules）

1. **绝对路径**：一律改写为相对路径或占位符（如 `<repo-root>`）。
2. **URL**：私密地址不出现；必须引用时使用占位符（如 `https://<review-host>/`）。
3. **ID 与账号**：应用 ID、开发者 ID、广告位 ID、榜单 ID、用户 ID 一律占位符化。
4. **真实姓名**：不出现；以角色名（Human Product Owner、创始人、负责人）代替。
5. **提交历史**：公开镜像不携带生产仓库历史（见下节），正文引用内部提交时只给角色与日期，不给提交 SHA 或私有分支名。
6. **数字口径**：可公开的度量（如测试数量、模拟局数、验证结果）以公开镜像内可复现的数据为准；含内部口径的原文不复制。
7. **新增内容**：所有新增文档在合并前执行一次 `rg` 级扫描（如 `rg "<LOCAL_PATH>|<PRIVATE_URL>|<app-id>|<account-keyword>"`），零命中才放行。

## 5. 不重写生产历史的决策

- **现状**：公开镜像仓库以单一基线快照提交起步，Git 历史从头建立，与内部生产仓库无共享提交。
- **决策理由**：
  1. 生产仓库历史包含私密信息（路径、站点、账号、平台标识），逐提交改写成本高、易漏；
  2. 本项目开发过程由 AI 辅助完成，历史提交混合了私人工作区与评审过程，不适合原样公开；
  3. 单一基线使公开仓库具备干净、可审计的起点，也符合"版本事实以公开镜像为准"的治理口径。
- **含义**：
  - 不尝试 `git filter-branch`/`filter-repo` 清洗生产历史；
  - 公开镜像从基线快照之后的所有提交都是公开、可讨论的；
  - 生产仓库与公开镜像不再保持逐提交同步，而是以"版本发布"为同步单位。

## 6. 同步与验收

- 每次发布版本（见 `docs/oss/RELEASE_AND_MAINTENANCE_PLAN.md`）由维护者按本节范围从生产候选整理出公开基线。
- 放行前检查：范围 ⊆ 公开范围；排除清单零收录；脱敏扫描零命中；许可与资产审计记录存在。
- 记录检查结果于版本发布的 PR/issue，作为该版本的脱敏证据。
